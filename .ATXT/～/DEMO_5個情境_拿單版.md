## 下午 DEMO：5 個情境（拿單版）

你今天的目標不是「展示技術」，是讓對方相信：
- **流程順**（操作者爽）
- **不會崩**（出事有交代）
- **可交付**（能匯出、能留痕、能對接）

下面 5 個情境按「成交機率」排序。每個都附：目標、操作、你要講的話、成功判準、備案（Plan B）。

---

### DEMO 前 5 分鐘準備（一定要做）

#### A. 先決定今天走哪個 backend

你有兩條路：

1) **穩到爆（離線/dummy）**：不怕網路、不怕模型、不怕權限  
   - 適合：你要保證 demo 不翻車
2) **效果好（真實 Ollama）**：自然語言回答更像產品  
   - 適合：你確定現場機器有 Ollama + 已 pull 好 model

切換方式（環境變數）：

- 離線穩定：

```bash
export ECS_LLM_BACKEND=dummy
export ECS_VECTORSTORE_BACKEND=naive
```

- 真實 Ollama（你本機有 Ollama 才用）：

```bash
export ECS_LLM_BACKEND=ollama
export ECS_OLLAMA_MODEL="qwen2.5:14b"
```

> 你可以「先用 dummy 保命」，如果現場狀況很好，再切到 ollama 做加分 demo。

#### B. 先準備 2 份文件

- **文件 1（合約）**：你要 demo 的客戶合約（或 sample_contract.pdf / sample_rule.docx）
- **文件 2（公司規範/紅線）**：付款條件/保固/保密/管轄等（用 docx/txt 也可）

> demo 的重點是「你能把他們的規範變成可查詢的 evidence」，不是模型很會講。

## 情境 1：上傳→索引→一問命中（最小端到端，先建立信任）

### 目標
讓對方看到：**操作簡單、速度可控、系統不崩、第一問就命中條款**。

### 操作步驟（你照做就好）
1. 開 Streamlit（你的現有 UI：企業合約守門員）
2. 上傳文件（PDF/DOCX）
3. 點 `🚀 開始索引 (讀取文件)`  
   - 讓他看到：字數、chunk 數量
4. 問一個「會命中」的問題：
   - 例：`逾期付款會怎樣？` / `保密期限多久？`
5. 展示：
   - `🟢/🔴` 風險燈號
   - tabs：現況/風險/建議/證據原文

### 你要講的話（成交語言）
- 「我們先讓操作者**有感**：上傳、索引、問答都是可控流程，且每次回答都能看到 evidence。」

### 成功判準
- 有顯示 evidence（證據片段）
- 回答有結構（現況/風險/建議）

### Plan B（翻車時）
- 如果 PDF 抽不到字：立刻說「這份是掃描 PDF，需要 OCR；我們 ingestion 會回報原因，不會崩。」  
  → 切換到 docx/txt demo

---

## 情境 2：證據導向（把「為什麼」說清楚，避免『模型幻覺』疑慮）

### 目標
對方最怕的是 AI 胡說。你要讓他看到：**結論不是憑空來的**。

### 操作
1. 問一個風險問題（越敏感越好）：
   - `Change of Control 的門檻是多少？`
   - `保證人責任的範圍？`
2. 直接點「📄 證據原文(Debug)」tab
3. 讓他看到：AI 看到的片段就是合約本身

### 話術
- 「我們不是只給答案，我們給的是**可審核的證據鏈**。這是企業最在意的。」

### 成功判準
- evidence 片段清晰可讀

### Plan B
- 如果回答品質一般：你把重點移到 evidence（「至少不會胡說」），並說「真實 LLM/embedding 上線後，品質會更強，但產品先保證可審核。」

---

## 情境 3：歧義偵測→請操作者決策（CONSULT 模式，超像企業流程）

### 目標
展示你不是“硬答”，而是能在歧義時 **升級成流程**：請人做決策，避免錯判。

### 操作
1. 準備一段含多門檻的條款（例：30% 與 50% 都出現）
2. 問：
   - `What is the threshold for Change of Control?`
3. 系統應回 `CONSULT`（請你選融資/營運授權）

### 話術
- 「企業真正需要的是：遇到歧義時，系統能把問題**升級成工作流**，而不是硬編答案。」

### 成功判準
- 系統進入 CONSULT（不是 REPORT）
- 文案清楚指引下一步（要選哪一類）

### Plan B
- 如果這份文件沒有歧義：換你內建的測試文本（或用你準備的公司規範文件）

---

## 情境 4：一鍵重置（多文件、多輪對話不串台）

### 目標
展示「操作者不會被上一份文件污染」，這是最常見痛點。

### 操作
1. 上傳文件 A → 索引 → 問題 → 得到結果
2. 點 `🔄 清除所有記憶 (重置系統)`
3. 上傳文件 B → 索引 → 問同樣問題 → 結果應該不同

### 話術
- 「我們把‘狀態管理’當成產品層級問題處理：可以重置，避免串台，操作者才敢用。」

### 成功判準
- reset 後不會用到舊 evidence

### Plan B
- 如果你擔心現場 cache：重置後直接重整頁面，並重新索引

## 情境 5：匯出交付（把價值從『聊天』變成『可交付成果』）

### 目標
這一段最像「你在賣 $5k-$15k 的固定價格交付」：你不是 demo 聊天，你是在 demo 交付物。

### 操作
1. 做完一次 REPORT
2. 往下捲，會看到「📤 匯出本次分析（可交付）」  
3. 點：
   - `⬇️ 下載 Markdown 報告`
   - `⬇️ 下載 JSON（系統對接用）`
4. 打開 markdown 給他看：包含問題、風險、現況/風險/建議、證據片段

### 話術
- 「這就是交付物：可直接進你們內部系統/工單/法務審核流程，不是一次性的聊天。」

### 成功判準
- 能下載成功
- 檔案內容包含 evidence（對方會覺得『可用』）

### Plan B
- 如果下載被瀏覽器擋：改用複製貼上（tabs 內容 + evidence）

## 你今天的「成交結構」（你照這個講）

1. **先證明能跑（情境 1）**
2. **再證明可信（情境 2）**
3. **再證明不亂答（情境 3）**
4. **再證明操作者爽（情境 4）**
5. **最後證明可交付（情境 5）**
